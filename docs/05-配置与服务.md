# 配置与服务

## 插件配置

插件通过 `cordis.yml` 接受配置。导出同名的 `Config` 类型和 Schemastery schema，默认值直接放在 schema 字段上：

```ts
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'

export const name = 'my-plugin'

export interface Config {
  greeting: string
  maxRetries: number
  verbose?: boolean
}

export const Config: Schema<Config> = Schema.object({
  greeting: Schema.string().default('Hello'),
  maxRetries: Schema.number().default(3),
  verbose: Schema.boolean().default(false),
})

export function apply(ctx: Context, config: Config) {
  console.log(config.greeting)  // 用户值或 schema 默认值
}
```

在 patch 行里提供配置：

```yaml
- insert:
    - id: my-plugin
      name: dsh-my-plugin
      config:
        greeting: 'Hi there'
        maxRetries: 5
```

要点：

- `z` / `Schema` 从 `@deepseek-ai/schemastery` 导入，**不是 zod**。
- 不要导出普通对象作为 `Config`，它不实现 Cordis 需要的 Standard Schema 接口。
- schema 在插件加载时运行校验并填充默认值；非法配置让加载失败并给出可操作的错误。
- 更严格的校验：`Schema.string().required()`、`Schema.union(['fast', 'accurate']).default('fast')` 等。

**设计原则**：

- **不硬编码可调值**：任何两个部署可能想设置得不同的值都必须是配置字段。检验标准：`cordis.yml` 能否不改代码就改这个值。
- **非法配置要 fail loud**：自包含的约束写进 schema，让它在加载期失败；涉及服务或已注册资源的引用走依赖注入。
- **HMR**：配置编辑会热替换插件——卸载旧实例、加载新实例。注册项是 effect 所以自动清理。

## 服务与依赖注入

服务是一个插件向其他插件暴露的能力。`tools`、`llm`、`agents` 都是服务，每个都是挂在 `ctx` 上的命名能力。

**消费服务：inject**

```ts
export const inject = ['tools']

export function apply(ctx: Context) {
  // 这里 ctx.tools 一定就绪
  ctx.tools.register(/* ... */)
}
```

`apply` 运行时，`inject` 声明的每个服务都已就绪。服务未就绪时插件等待而不是运行。**`ctx.<name>` 只有在 inject 里声明的服务才可用。**

**可选依赖：ctx.get**

```ts
export function apply(ctx: Context) {
  const metrics = ctx.get('metrics')   // 可选服务，可能 undefined
  metrics?.record('plugin_loaded', 1)
}
```

可选服务用 `ctx.get()` 在使用点判断，不要写进 `inject`。也不要写 `ctx.get('webServer') ?? ctx.get('httpServer')` 之外的硬绑定——服务名在演进（`httpServer` → `webServer`）。

**提供服务：Service 类**

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

export default class MetricsService extends Service {
  static inject = ['llm']   // 服务可以依赖其他服务

  constructor(ctx: Context) {
    super(ctx, 'metrics')    // 'metrics' 是服务名
  }

  record(event: string, value: number) { /* ... */ }
}
```

加载后，消费者用 `ctx.metrics` 访问。用 TypeScript 声明合并给 `ctx.metrics` 提供类型：

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    metrics: MetricsService
  }
}

export default class MetricsService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'metrics')
  }
  record(event: string, value: number) { /* ... */ }
}
```

**服务消失的行为**：运行中必需服务消失（比如它的 provider 卸载）时，依赖插件自动 dispose，服务回来时重新加载。这防止插件调用已不存在的服务。

**服务隔离**：`cordis.yml` 可以用 `isolate` 让不同插件组看到同一服务的不同实例（如不同超时的 bash 实例），互不影响。

## 声明合并触发器

DSH 各包通过 `declare module '@deepseek-ai/cordis'` 扩展 `Context`。要看见对应成员，必须把该包加载进 TypeScript program：

```ts
import type {} from '@deepseek-ai/dsh-subagent'        // 让 ctx.subagents 类型可见
import type {} from '@deepseek-ai/dsh-system-prompt'   // 让 ctx.systemPrompt 类型可见
```

`import type {}` 是编译期擦除的，不进产物。

## 挂载时机的坑

`inject` 只等服务（service 已提供），**不等 provider 注册**（同一服务下另一行插件的 effect）。provider 注册是兄弟插件行的 effect，Loader 并发激活下可能晚于你的 `apply`。任何"依赖兄弟插件行为"的校验必须延迟到首次真正使用的地方（最早可解析点 fail-loud），不要在 `apply` 里校验 provider 存在。
